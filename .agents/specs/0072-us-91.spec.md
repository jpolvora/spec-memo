# Specification — OpenCode v2: generated plugin fails to load — emit default { id, setup } instead of legacy { name, onInit, onPrompt, onExit }

## Description

### Problem statement

`memo install-hooks --host opencode` (also reached through `memo setup`) writes a managed OpenCode plugin whose default export is a Cursor-style lifecycle object:

```js
export default {
  name: 'spec-memo',
  async onInit() { /* memo bootstrap + prompt session_start */ },
  async onPrompt() { /* memo prompt record */ },
  async onExit() { /* memo prompt session_end + sync */ },
};
```

OpenCode's external plugin loader validates the default export against `{ id: string, effect: function } | { id: string, setup: function }`. The emitted object has no `id`, no `effect`, and no `setup`, so schema decoding fails and the module is **silently dropped** with a single `WARN … failed to load plugin` line in the OpenCode server log. No user-visible error is produced; the only symptom is that session memory never records anything.

The three lifecycle names in the template (`onInit`, `onPrompt`, `onExit`) are not OpenCode plugin hooks at all — in OpenCode v2 hooks are registered on domains inside `setup` (`ctx.session.hook("prompt", …)`, `ctx.event.subscribe(…)`), and teardown is a cleanup function returned by `setup`.

### Generation site and blast radius

| Concern | Location | Current state |
|---------|----------|---------------|
| Generator | `src/hooks-install.ts` → `generateOpenCodePlugin(version, memoExecutable, memoArgs, memoShell)` | Emits the legacy `{ name, onInit, onPrompt, onExit }` template literal |
| Artifact wiring | `src/hooks-install.ts` → `buildHostArtifacts` (`case 'opencode'`) | Unchanged; writes `spec-memo.js` with `kind: 'js'` |
| Managed targets | `src/hooks-install.ts` → hook-target table (`case 'opencode'`) | Local `{productRoot}/.opencode/plugins/spec-memo.js`; global `~/.config/opencode/plugins/spec-memo.js` |
| Diagnostics | `src/hooks-install.ts` → `inspectAgentHooks` (`case 'opencode'`) | Reads both targets and flags `outdated` when `generated-by` differs from the running package version |
| Removal | `src/hooks-install.ts` → `removeSpecMemoBlock` | Deletes a managed `.js` file when it carries the `generated-by` marker; the marker must survive this fix |
| Tests | `src/hooks-install.test.ts` → `opencode plugin includes init/prompt/exit handlers per AC7` | Asserts `/onInit/`, `/onPrompt/`, `/onExit/` — **enshrines the broken shape** |
| Session state | `ACTIVE_SESSION_FILE = '.spec-memo/.active-session-id'`, `HOOK_TIMEOUT_MS = 1500` | Written relative to process cwd; bounded by a fail-open timeout |

### Technical scope

1. **Entrypoint shape.** Rewrite the generated module's default export to `{ id: 'spec-memo', setup, server }` — the documented dual-entrypoint form covering v2 (`{ id, setup }`) and v1 object entrypoints (`server()`, OpenCode `>= 1.18.29`). Keep the fail-open `runMemo` spawn helper, the `HOOK_TIMEOUT_MS` bound, and the `generated-by` marker.
2. **Lifecycle mapping.** `onInit` → the body of `setup`; `onExit` → the cleanup function returned by `setup`; `onPrompt` → a registration obtained from `ctx.session.hook("prompt", …)`.
3. **Working-directory resolution.** The generated plugin currently writes `.spec-memo/.active-session-id` relative to the process cwd. Under OpenCode the plugin's project location is `ctx.location.directory`; the session file and every spawned `memo` child must resolve against it.
4. **Registration disposal.** `ctx.session.hook(...)` returns a registration that must be disposed (or the cleanup function must run) so no child process outlives the plugin.
5. **Test contract.** `hooks-install.test.ts` must assert the v2 shape; the legacy-token assertions must be removed or inverted.
6. **Stale pre-fix artifacts.** An artifact written by an older package version stays on disk and keeps failing after an upgrade. `inspectAgentHooks` already reports `outdated` for a version mismatch — reuse it rather than adding a new diagnostic surface, and keep the existing `--force` overwrite contract (`writeFileAtomic` → `backupIfNeeded`).

### Behavioral parity target

After the fix, a plugin that loads must still perform: `memo bootstrap`, `memo prompt session_start`, one `memo prompt record` per recorded turn, `memo prompt session_end`, and `memo sync` on unload. Parity is **best-effort by design**: the OpenCode `prompt` hook fires on user-prompt admission only — synthetic messages, shell messages, compaction controls, and move controls do not trigger it — so turn coverage under v2 is narrower than the legacy Cursor-style `onPrompt` implied. See the companion `{specsDir}/0072-us-91.context.md` for the recorded gray areas.

## Acceptance Criteria

- AC1: The plugin generator shall emit a default export containing `id: 'spec-memo'` and a `setup` function, and shall omit `name`, `onInit`, `onPrompt`, and `onExit` from that default export.
- AC2: The plugin generator shall declare the default export as a plain object literal with `id`, `setup`, and `server` keys so the module loads without resolving `@opencode/plugin` at runtime and OpenCode v1 hosts (object entrypoint, `>= 1.18.29`) can register hooks through `server()`.
- AC2b: Where an OpenCode v1 host invokes `server(input)`, the generated plugin shall resolve the working directory from `input.directory` (falling back to the process cwd), start the session, and return v1 hooks `chat.message` (one `memo prompt record` per message) plus `dispose` (session end + unlink + `memo sync`).
- AC3: The generated plugin shall keep `// generated-by: spec-memo@{version}` as its first line so `extractGeneratedVersion` version detection and `removeSpecMemoBlock` deletion keep working.
- AC4: When `memo install-hooks --host opencode --apply` runs without `--global`, the installer shall write the generated plugin to `{productRoot}/.opencode/plugins/spec-memo.js`.
- AC5: When `memo install-hooks --host opencode --apply --global` runs, the installer shall write the generated plugin to `~/.config/opencode/plugins/spec-memo.js`.
- AC6: When OpenCode invokes the plugin's `setup`, the generated plugin shall spawn `memo bootstrap` and then `memo prompt session_start --session-id {sid}` with the child process working directory set to `ctx.location.directory`.
- AC7: When the plugin's `setup` completes, the generated plugin shall register the turn-recording prompt hook only after `memo bootstrap` and `memo prompt session_start` have both resolved, so no turn is recorded before the session exists.
- AC8: When a user prompt is admitted through the OpenCode prompt hook, the generated plugin shall spawn exactly one `memo prompt record --session-id {sid} --body '[hook-automated turn]'` for that prompt, reusing the session id created during `setup`.
- AC9: When the cleanup function returned by `setup` runs, the generated plugin shall dispose its hook registration before spawning `memo prompt session_end --session-id {sid}` and `memo sync`, and shall unlink the active session id file.
- AC10: The generated plugin shall bound every spawned `memo` child process with the `HOOK_TIMEOUT_MS` timeout of 1500 ms and shall resolve without throwing when the child errors, exits non-zero, or is killed on timeout.
- AC11: While the active session id file is missing or unreadable, the generated plugin shall fall back to a `hook-${Date.now()}` identifier without throwing.
- AC12: The generated plugin shall resolve the active session id file against `ctx.location.directory` and shall not create `.spec-memo/.active-session-id` relative to the OpenCode server process cwd.
- AC13: If the generated plugin's `setup` throws while spawning `memo`, then the plugin shall swallow the error so OpenCode's plugin loader is unaffected.
- AC14: If an existing managed `spec-memo.js` differs from the generated content and `--force` was not passed, then the installer shall exit non-zero with the existing `Target exists and differs` message instead of silently rewriting the artifact.
- AC15: When `memo doctor` inspects a managed OpenCode plugin artifact whose `generated-by` version differs from the running package version, the `doctor` inspection shall report the `Opencode` host entry with `outdated: true`.
- AC16: When `npm test` runs the hooks-install suite, the suite shall assert the dual-entrypoint shape (`id` + `setup` for v2, `server` for v1) and shall no longer assert the presence of `onInit`, `onPrompt`, or `onExit`.
- AC17: Where `fable.enabled` is true, the implementation shall pass the stack invariant scan for the `typescript-node` stack without introducing a floating promise or an unchecked `any` in the generated template or the generator.

## Notes

- **Stack invariants applied (`typescript-node`).** Zero floating promises: the abort-controller subscription pattern and every `runMemo` call are awaited or explicitly void-marked; timers are cleared on both `error` and `close`. No unchecked `any` / `@ts-ignore`. Injection/path-traversal: the child is `spawn`-ed with an argument array (`[...memoArgs, ...args]`), never a concatenated command string, and the project directory comes from `ctx.location.directory` rather than string-built paths. Resource lifecycle: registrations and the active session id file are released in the cleanup function returned by `setup`.
- **Fail-open is a product invariant, not an accident.** Every spawned `memo` call is bounded by `HOOK_TIMEOUT_MS` and resolves to `0` on error, timeout, or non-zero exit. Memory capture must never break or hang the host editor.
- **Generators are string templates.** `generateOpenCodePlugin` interpolates `JSON.stringify(memoExecutable)` and `JSON.stringify(memoArgs)` into a template literal; any new template literal must keep that escaping discipline so Windows paths and arguments cannot break the emitted module.
- **`extractGeneratedVersion` and `removeSpecMemoBlock` depend on the header comment.** Any rewrite must keep `// generated-by: spec-memo@{version}` on line 1 — this is also what makes stale-artifact detection possible (AC15).
- **`inspectAgentHooks` shares one `version` variable across all scanned paths for a host.** With two managed copies at different versions, the last path scanned wins. That is pre-existing behavior and is **not** fixed here; the Out of Scope table records it so the implementer does not silently widen the diff.
- **ESM vs CJS.** The managed artifact is written as `.js`. The current template uses ESM (`import * as fs`, `export default`) and loads under OpenCode's plugin loader today; keep ESM. Do not introduce `require`.
- **Windows specifics.** `memoShell` defaults to `process.platform === 'win32'`; keep that default so the `memo` shim resolves, and keep the assertion that `shell: true` / `shell: false` is emitted for the two cases (AC-observable in the existing test).

## Original Issue Context

Verbatim human-authored content from https://github.com/jpolvora/spec-memo/issues/91 (state: open at import time).

### Summary

The OpenCode plugin generated by `memo setup --host opencode` (spec-memo **0.37.8**) fails to load under **OpenCode v2** (observed on v2.0.24). The failed step is `generateOpenCodePlugin`, which emits a legacy Cursor-style object:

```js
// generated-by: spec-memo@0.37.8
export default {
  name: 'spec-memo',
  async onInit() { /* memo bootstrap + prompt session_start */ },
  async onPrompt() { /* memo prompt record */ },
  async onExit() { /* memo prompt session_end + sync */ },
};
```

OpenCode v2 only accepts a default export shaped as `{ id, effect }` or `{ id, setup }`, so the module is dropped with a WARN (no visible error to the user).

### Environment

- OS: Windows (win32), Node >= 22
- OpenCode: **v2.0.24** (server runtime)
- spec-memo: **0.37.8** (`memo` CLI, installed from GitHub — `spec-memo` is not published on npm)
- Generated files (both loaded, both fail):
  - `C:\Users\jpolv\.opencode\plugins\spec-memo.js` (stale, `generated-by: spec-memo@0.26.1`)
  - `C:\Users\jpolv\.config\opencode\plugins\spec-memo.js` (`generated-by: spec-memo@0.37.8`)

### Evidence (server log)

```
timestamp=2026-10-07T18:47:49.952Z level=WARN run=f5ed8712 message="failed to load plugin"
  target="C:\Users\jpolv\.opencode\plugins\spec-memo.js" ref=err_d69e0238
  cause="Cause([Fail(PluginModule.LoadError: Plugin must export a default definition with an id and an
  effect or setup function. (cause: SchemaError(Missing key at [\"default\"][\"id\"])))])" role=server
```

The sibling `.config` copy fails identically (`ref=err_4b0b9cc8`). The same run shows the `spec-memo` MCP server connecting fine (`mcp connected server=spec-memo tools=11`), so only the plugin artifact is broken.

### Root cause

OpenCode v2's external plugin loader validates the module default export against this schema:

```
default: { id: string, effect: function } | { id: string, setup: function }
```

The template emits `{ name, onInit, onPrompt, onExit }` — no `id`, `effect`, or `setup` — so schema decoding fails and the plugin never loads. This is the same failure class documented upstream in the OpenCode repo (v1 `{ id, server }` module shape silently dropped): the only trace is a single `WARN … failed to load plugin` line in `~/.local/share/opencode/log/opencode.log`.

Note: on the V2 side, the erstwhile lifecycle names (`onInit`/`onPrompt`/`onExit`) are not OpenCode plugin hooks at all — V2 hooks are registered on domains (e.g. `ctx.session.hook("prompt", …)`, `ctx.event.subscribe(…)`, cleanup returned from `setup`).

### Where it is generated

`dist/hooks-install.js` → `generateOpenCodePlugin(version, memoExecutable, memoArgs, memoShell)` — the template literal containing `export default { name: 'spec-memo', async onInit() … }`. The test suite currently enshrines the bad shape: `dist/hooks-install.test.js` asserts `/onInit/`, `/onPrompt/`, `/onExit/` are present in the generated OpenCode plugin.

### Expected

The generated OpenCode plugin loads on v2 and performs the existing behavior: `memo bootstrap`, `memo prompt session_start`, per-turn `memo prompt record`, `memo prompt session_end`, and `memo sync` on unload.

### Suggested fix

Emit a v2 definition, e.g.:

```js
import { Plugin } from '@opencode/plugin';

export default Plugin.define({
  id: 'spec-memo',
  async setup(ctx) {
    const cwd = ctx.location.directory;
    // memo bootstrap + prompt session_start (cwd = project directory)
    // record turns via ctx.session.hook('prompt', ...) or ctx.event.subscribe(...)
    return () => {
      // memo prompt session_end + sync
    };
  },
});
```

If older V1 releases must keep working, use the documented dual entrypoint (V1 `server()` + V2 `setup()` from one default export; V1 object entrypoints require OpenCode `>= 1.18.29`):

```js
export default {
  ...Plugin.define({ id: 'spec-memo', async setup(ctx) { /* v2 */ } }),
  async server() { return { /* v1 hooks */ }; },
};
```

Additional points:

- Resolve the working directory from `ctx.location.directory` (or use `ctx.$`) instead of relying on process cwd for `.spec-memo/.active-session-id`.
- Update `hooks-install.test.js` to assert the new `id` + `setup`/`effect` shape.
- The `.opencode/plugins/spec-memo.js` artifact left on disk at `spec-memo@0.26.1` predates the current generator output; regeneration should overwrite/reconcile both known plugin paths.

### Design Intent

`git log -S "onInit" -- src/hooks-install.ts` → `735ff36 feat(hooks): add memo install-hooks CLI and doctor diagnostics (0.21.0)` is the **only** commit that ever introduced or changed the legacy entrypoint.

- No commit message, code comment, or documentation claims OpenCode compatibility for `{ name, onInit, onPrompt, onExit }`. The three names are Cursor's hook lifecycle vocabulary (`SessionStart` / `UserPromptSubmit` / `SessionEnd` equivalents), and Cursor support was implemented separately through `generateCursorHooksJson` + `generateCursorRule`.
- `src/hooks-install.test.ts` block `opencode plugin includes init/prompt/exit handlers per AC7` asserts the presence of `onInit` / `onPrompt` / `onExit`, which converted an unverified guess into an enforced contract — the mechanism that let the gap survive every subsequent release.
- **Verdict: accidental gap, not an intentional compatibility constraint.** The shape was never validated against a running OpenCode host, and it matches no documented OpenCode release (v1 expects a plugin function returning hooks, v2 expects `{ id, effect | setup }`). There is therefore no behavior to restore and no backward-compatibility obligation.
- The stale `0.26.1` artifact on disk is explained by the same gap: that file was written by an early generator and is still being loaded by the host, so the failure persists until it is regenerated (AC15 + AC5).
