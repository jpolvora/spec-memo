# Specification — Probe noise: unauthenticated local health checks flood error.logs and failure telemetry; status companion has no /health

**State:** open
**Labels:** bug

## Description

Unauthenticated local probes on the SSE listener (`src/server.ts`) and the status companion (`src/status.ts`) write a full WARN `error.logs` block on every request and, on the SSE listener, record `success: false` / `HTTP_401` telemetry. The status companion has no `/health` route, so a generic health check becomes `Route not found` (404 WARN) while the same path on the SSE port is an unauthorized 401 WARN.

The product must keep real authorization failures visible, keep `HTTP_401` queryable, and leave authorized client behavior unchanged. Repeated unauthorized requests from the same client must collapse to a bounded log (first occurrence plus a periodic rollup), and unauthenticated local probes must not inflate the product failure rate. `GET /health` on the status companion must return a lightweight health response consistent with the SSE listener and must not emit a route-not-found WARN.

## Acceptance Criteria

- AC1: A burst of N unauthenticated requests to an existing protected status or SSE route appends O(1) `error.logs` entries for that client (first occurrence plus at most one rollup in the window), not N full multi-line blocks.
- AC2: The first unauthorized request in a burst remains a WARN that an operator can read; later repeats in the window are not each a full block.
- AC3: `GET /health` on the status companion returns 200 or 204 with a small health body or empty success, and does not log `Route not found`.
- AC4: A token-less `GET /health` on the status companion does not log an unauthorized WARN when `/health` is treated as a silent probe.
- AC5: SSE and status still return 401 for protected routes when the token is missing or wrong. A distinct client, or the first request after the rollup window, still produces an observable WARN.
- AC6: Authorized requests to protected routes keep their current status codes and payloads.
- AC7: `HTTP_401` remains present in telemetry query results, and unauthenticated local probe 401s are excluded from the product failure-rate numerator.
- AC8: Regression tests cover the burst log bound, status `/health`, and failure-rate exclusion. A test that expects a full WARN block per unauthorized request fails until the bound exists.

## Original Issue Context

## Summary

Two diagnostics-noise defects of the same class as #68 (silent probe routes), but for auth and health probes:

1. **Every unauthenticated request is logged (and, on the SSE listener, counted as a failure).** A single local health-poller produced **179 `status-server` WARN blocks** for `GET /api/status` in a ~3-minute window (~9 req/s), plus **1 `sse-server` WARN** for `GET /health`. On the SSE listener the same request also records a `success:false` `HTTP_401` telemetry event (`src/server.ts:266-271`, `290-308`).
2. **The status companion serves no `/health`.** Generic health checks aimed at the status port fall through to `Route not found: GET /health` (`src/status.ts:7951`), while the SSE listener on the other port answers `/health`. A token-less `/health` probe is therefore a WARN 404 on one port and a WARN 401 on the other — neither is a real incident.

Combined, these dominated the operator's `error.logs` (180 of ~215 WARN/ERROR entries) and inflated the failure-rate metric.

## Evidence (observed on a real vault)

Counts across one `error.logs` file (~215 WARN/ERROR entries total):

| Subsystem | Count | Endpoint | Message |
|---|---|---|---|
| `status-server` | 179 | `GET /api/status` | `Unauthorized request: missing or invalid authorization token` |
| `sse-server` | 1 | `GET /health` | `Unauthorized request: missing or invalid authorization token` |
| `status-server` | 2 | `GET /health` | `Route not found: GET /health` |

The 179 requests arrived in a burst at ~9/s for ~3 minutes; the client was a local HTTP client (browser-style user-agent, no `Authorization` header), i.e. a naive local health poller, not an attacker.

`memo doctor --json` telemetry for the same vault:

```json
"failureRate": 0.09,
"topErrorCodes": [ { "code": "EXIT_1", "count": 252 }, { "code": "HTTP_401", "count": 170 }, ... ]
```

## Root cause / code references

- Status companion, per-request WARN on `/api/*`:
  ```ts
  // src/status.ts:5965
  if (pathname.startsWith("/api/")) {
    if (!isAuthorized(req, url, authToken)) {
      logErrorReport({ subsystem: "status-server", ..., level: "WARN", ... }); // full block per request
      writeJson(res, 401, { error: "Unauthorized" });
      return;
    }
  }
  ```
- SSE listener, per-request WARN **plus** failure telemetry:
  ```ts
  // src/server.ts:290
  if (!isAuthorized(req, url, authToken)) {
    capturedOp = "unauthorized_access";
    logErrorReport({ subsystem: "sse-server", ..., level: "WARN", ... });
    res.writeHead(401, ...); return;
  }
  // src/server.ts:266 (finish handler)
  recordTelemetry({ category: 'http_endpoint', success: statusCode < 400, errorCode: statusCode >= 400 ? `HTTP_${statusCode}` : undefined, ... });
  ```
- The status companion silent-probe allowlist (`src/status.ts:5848-5851`) covers `favicon.ico`, `robots.txt`, `/json/version`, and the Chrome DevTools well-known path, but **not** `/health`; the status server registers no `/health` route at all.

## Impact

- `error.logs` is dominated by probe noise (84% of entries here), burying real incidents; the log grows with polling rate.
- The failure-rate metric counts authentication rejections of local probes as failures (`HTTP_401` is a top error code), so health dashboards look unhealthy for a correctly configured vault.
- Operators are nudged to "fix" an auth setup that is actually correct.

## Proposed fix

- **Bounded auth logging:** aggregate/rate-limit repeated unauthorized requests per client/IP — log the first occurrence and a periodic rollup count instead of one full multi-line block per request (or demote repeats to debug). Keep the first failure visible so a real misconfiguration is still surfaced.
- **Telemetry classification:** keep `HTTP_401` queryable but exclude unauthenticated local probes from the product-failure rate (they are expected, not faults).
- **`/health` parity:** serve a lightweight `/health` on the status companion (200/204, consistent with the SSE listener) so generic health checks do not produce `Route not found` WARNs. Add `/health` to the silent-probe treatment if it must remain unauthenticated without logging.

## Acceptance

- A burst of N unauthenticated local requests appends O(1) `error.logs` entries (e.g., first + rollup), not N full blocks.
- `GET /health` on the status companion returns a health response (no `Route not found` WARN).
- Real authorization failures remain observable and are not silently dropped.
- Authz behavior for legitimate clients is unchanged.

### Prior Work Sweep

Open pull requests on `jpolvora/spec-memo`: none (2026-09-29). No open PR names issue 87. Related closed work is issue #68 (silent probe routes for favicon and DevTools); this spec extends that class to auth bursts and status `/health`.

### Design Intent

Per-request unauthorized WARNs and counting HTTP 4xx as telemetry failures are the current implementation, not a documented product rule that probes must flood `error.logs`. Issue #68 already treats known local probes as silent. Collapsing repeat 401s and serving status `/health` closes an accidental gap.
