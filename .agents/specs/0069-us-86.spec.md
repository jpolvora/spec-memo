# Specification — Indexer leaves stale FTS row when a record id changes (duplicate hits + doctor consistent:false)

**State:** open
**Labels:** bug

## Description

`indexRecord` in `src/indexer.ts` deletes the previous `records_fts` row by `id` + `projectId` only. Frontmatter `id` can change on rename, re-slug, or import normalization while `filepath` stays the stable identity. The old id row remains, so one file has two FTS rows. Search can return a ghost id, and `memo doctor` reports `consistent: false` with that id in `unexpectedIds` until `memo doctor --rebuild`.

`record_links` rows keyed by `source_id` for the previous id must be removed or retargeted in the same re-index. A full rebuild that truncates or reconciles by filepath must not recreate the duplicate. After an id change and re-index, doctor must report `consistent: true` without a rebuild.

## Acceptance Criteria

- AC1: Re-indexing a markdown record whose frontmatter `id` changed leaves exactly one `records_fts` row for that `filepath` and `projectId`.
- AC2: The surviving row's `id` equals the new frontmatter id. The previous id is absent from `records_fts` for that project.
- AC3: `record_links` has no edges whose `source_id` is the previous id for that project after re-index, unless those edges were rewritten to the new id.
- AC4: `memo doctor` FTS consistency is `consistent: true` with empty `unexpectedIds` and empty `missingIds` after the rename, without `--rebuild`.
- AC5: Search does not return the obsolete id for that file. Get-by-old-id does not resolve the file.
- AC6: Re-index of an unchanged id still replaces that id's row once and does not delete a different file that shares no filepath.
- AC7: A regression test upserts a record, changes its id, re-indexes, and asserts one row per filepath plus no `unexpectedIds`. The test fails on current `DELETE ... WHERE id = ? AND projectId = ?` behavior.

## Original Issue Context

## Summary

`indexRecord` (`src/indexer.ts:185`) deletes the existing FTS row using **`id + projectId` only**. A record's `id` is mutable (it changes on rename / re-slug / import normalization), while `filepath` is the stable identity. When the `id` changes, the row keyed by the previous id is never removed, so `records_fts` ends up with **two rows pointing at the same file**. Search can surface a ghost hit whose id no longer exists as a file, and `memo doctor` reports `consistent: false` (`unexpectedIds`) for a vault that is otherwise healthy. `memo doctor --rebuild` clears the symptom, but the defect recurs on the next id change.

## Reproduction (observed on a real vault)

1. A record exists indexed under `id: <kind>-<slug>` (auto-derived shape).
2. Its frontmatter `id` is later changed to `<slug>` and re-indexed (git shows the transition `-id: <kind>-<slug>` / `+id: <slug>`).
3. Direct read-only query of `records_fts` by filepath:

```
filepaths with duplicate FTS rows: 1
[
  {
    "filepath": ".../projects/<projectId>/specs/<slug>.md",
    "n": 2,
    "ids": "<kind>-<slug> | <slug>"
  }
]
total rows: 3280 | distinct filepaths: 3279
```

`memo doctor --json` for the same vault:

```json
"fts": {
  "indexedRecordsCount": 3280,
  "markdownRecordFiles": 3280,
  "markdownRecordIds": 1913,
  "indexedDistinctIds": 1914,
  "consistent": false,
  "missingIds": [],
  "unexpectedIds": ["<kind>-<slug>"],
  "unexpectedCount": 1
}
```

Warning emitted:

```
FTS index identity mismatch: 0 missing / 1 unexpected — 1913 markdown ids / 3280 files vs 1914 indexed ids. Missing: none listed. Unexpected: <kind>-<slug>. Run memo doctor --rebuild.
```

## Impact

- `search` / `get`-by-id can return a duplicate or ghost hit for the same file under an obsolete id.
- `memo doctor` flags the index as inconsistent and inflates `indexedRecordsCount`, so operators chase a false drift and are told to rebuild a vault that has no real missing records.
- `record_links` is also keyed by `source_id` (`src/indexer.ts:199`, `DELETE ... WHERE source_id = ? AND source_project = ?`), so stale link edges for the old id can persist too.

## Root cause

```ts
// src/indexer.ts:185 (indexRecord)
const del = db.prepare('DELETE FROM records_fts WHERE id = ? AND projectId = ?');
del.run(id, projectId);
```

The delete key must include the stable file identity. Suggested fix:

```ts
db.prepare('DELETE FROM records_fts WHERE projectId = ? AND filepath = ?').run(projectId, filepath);
```

and reconcile `record_links` for the previous id when it changes. The full-rebuild insert path (`src/indexer.ts:917`) should be fine if it reconciles by filepath/truncates.

## Acceptance

- Re-indexing a record whose frontmatter `id` changed leaves exactly one `records_fts` row for that `filepath`.
- `memo doctor --json` reports `consistent: true` after such a rename (no rebuild needed).
- Regression test: upsert a record, mutate its `id`, re-index, assert one row per `filepath` and no `unexpectedIds`.

### Design Intent

Delete-by-id matches the case where id is stable. Filepath is already the on-disk identity used by doctor file counts. Leaving the old id row is an accidental gap: doctor already tells operators to rebuild, which clears the symptom and does not fix the next rename.

## Out of Scope

| Item | Reason |
|---|---|
| Forbidding frontmatter id changes | Ids stay mutable |
| Rewriting every historical vault in place outside re-index or doctor rebuild | Fix is on the index write path; rebuild remains a recovery tool |
| Changing FTS schema columns | Not required if delete key uses existing `filepath` |
