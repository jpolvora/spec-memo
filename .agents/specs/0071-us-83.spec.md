# Specification — autoMode should mean unattended: no yield at internal checkpoints

**State:** open

## Description

`defaults.autoMode: true` is documented as auto-selecting the recommended gate option and crossing step boundaries without a user halt. It does not forbid stopping at internal checkpoints (end of a DAG wave, green test run, end of step artifacts) to narrate progress and wait for another user turn.

When autoMode is on, `ws-spec-to-pr` and `ws-spec-to-pr-lite` must keep executing across those checkpoints until `status: completed`, `status: failed`, or a blocker in the closed list below. Progress goes to machine surfaces (`telemetry.jsonl`, state handoffs, gate history), not a user-facing stop. The stop-condition list lives in `ws-shared/runtime/gates.md`. Both orchestrator skills reference that section instead of copying a second contract.

Valid autoMode stops:

- The suite stays red after the retries the skill already allows.
- A destructive confirmation the product already requires a human to approve (backup, merge, or delete).
- Missing credentials or network that blocks the next command.
- Workflow `status: completed` or `status: failed`.

A green wave, a successful build, or a mid-step status report is not a stop.

This change is skill and runtime markdown consumed by agents. It does not change spec-memo TypeScript.

## Acceptance Criteria

- AC1: `gates.md` lists the autoMode stop conditions in one section and states that a green wave is not a stop.
- AC2: `ws-spec-to-pr` SKILL.md states that `autoMode: true` continues through internal checkpoints until completed, failed, or a listed blocker, and points at `gates.md` for the list.
- AC3: `ws-spec-to-pr-lite` SKILL.md states the same rule and points at the same `gates.md` section without a second stop-condition list.
- AC4: Both skills say progress under autoMode is written to telemetry, state handoffs, or gate history rather than ending the user turn.
- AC5: A reader can see that step-boundary gate auto-selection remains in place and is not replaced by this checkpoint rule.
- AC6: No product `src/` behavior change is required. A negative check is a doc review: the skills must not tell the agent to pause after a green wave when autoMode is true.

## Original Issue Context

## Problem

`autoMode` (full auto) currently means "auto-select the recommended gate option and proceed across **step boundaries** without halting" (`ws-spec-to-pr` SKILL.md, `setup.md`). It says nothing about **turn boundaries / internal checkpoints**, so agents still stop mid-workflow to report progress and wait for the next user prompt.

## Reproduction context

During a full-auto `ws-spec-to-pr` run on a large multi-AC spec (multi-node implementation DAG, ship intent):

- Steps 0–3 (classify, plan, interview, exec DAG) flowed without prompts — autoMode worked there.
- Inside Step 4 the agent finished the first implementation wave, verified green on the full suite, then **stopped to report** instead of continuing to the next wave.
- The operator had to ask whether the run was completed and what had happened — they expected unattended execution through ship.

No gate fired. The halt was purely the agent treating end-of-wave as a reporting point. That is the gap: the skill never forbids yielding at internal checkpoints under autoMode.

## Proposal

Amend `ws-spec-to-pr` + `ws-spec-to-pr-lite` SKILL.md and `ws-shared/runtime/gates.md` § autoMode:

1. When `autoMode: true`, the orchestrator **must not yield control at internal checkpoints** (end of DAG node/wave, green verification, end of step artifacts). Continue across turns until `status: completed`/`failed` or a real blocker.
2. Progress reporting goes to machine surfaces (`telemetry.jsonl`, state handoffs, `## Gate history`), not user turns.
3. Enumerate the **only** valid stop conditions under autoMode: red suite the agent cannot fix after reasonable retries, destructive-gate requiring explicit human confirm (backup/merge/delete), missing credentials/network, or `status: completed`.
4. A green wave is never a stop reason — it is evidence for the next wave.

## Acceptance

- Re-running the same full-auto invocation proceeds Step 0 → Step 9 with zero user prompts except real blockers.
- `gates.md` documents the stop-condition list; both orchs reference it (no duplicated contract).

### Design Intent

Step-boundary autoMode is intentional and stays. Yielding after a green implementation wave is not specified as a checkpoint; it is an omission. This spec adds the missing prohibition and a single stop list.
